# The compiler is the reviewer the frontend does not have

Kamosu's frontend is **Svelte 5 with SvelteKit on `adapter-static`, TypeScript, Tailwind 4 and Paraglide**. The Rust binary serves the built files, so SvelteKit's own server half is unused and is taken purely for its router and project layout.

The choice was not made on elegance, bundle size or familiarity. It was made on a single property Kamosu has and most projects do not: **nobody who can read this code will ever read it.** The first Operator is not a developer, there is no second engineer, and no reviewer stands between a generated component and a phone propped against a chopping board. Every part of the stack above is therefore chosen so that **the build fails rather than the kitchen does** — the same argument [ADR 0001](./0001-both-doors-generated-from-one-operation-catalogue.md) made for Rust, applied to the browser.

## Why

- **The honest evidence favoured React, and the honest reading of it did not.** [Web-Bench](https://arxiv.org/html/2505.07473v1) is the only real head-to-head on LLMs building multi-step web projects, and React beat Svelte in five of six models — in one case 65% to 25%. That is recorded here rather than buried, because a future reader will find it and wonder. Two things move it: turning reasoning on took that same model from 25% to 55% on Svelte while barely moving React, so the gap is a capability gap that closes as models improve; and [SvelteBench](https://github.com/khromov/svelte-bench), which tests Svelte 5 runes specifically, is now saturated — Claude Opus 4.5 scores 100%. Kamosu is built by frontier models, not by the models in that table.
- **The remaining risk is stale knowledge, and Svelte ships the cure.** The failure Web-Bench actually measures is a model reaching for Svelte 4 habits instead of Svelte 5 runes. Svelte publishes documentation written for models — `llms-small.txt`, `llms-medium.txt`, `llms-full.txt` at [svelte.dev/docs/llms](https://svelte.dev/docs/llms). React ships no equivalent, because it has never needed one. A gap caused by thin training data is closable at build time in a way a general popularity advantage is not.
- **Beauty was flat between the candidates, so nothing aesthetic was traded away.** The signature native-feeling move — a recipe card expanding into its page rather than the screen swapping — used to require a framework's animation library and was React's strongest claim here. It is now the **View Transitions API**: plain CSS, Safari 18+, roughly 90% of browsers, identical in either framework. And the design work in this house happens in hand-written HTML mockups before a framework exists, as both SwoleMate's `mockups/` and [#13](https://github.com/BatterWorks/Kamosu/issues/13)'s `prototypes/13-look-and-feel/` did. The framework reproduces a look; it does not produce one.
- **Svelte's compiler warns about accessibility; React's has nothing equivalent.** Missing labels, unreachable controls, targets too small. For an app operated at arm's length with wet hands, that is a reviewer working for free on exactly the axis that matters.
- **Every layer above was then chosen for the same reason.** `svelte-check` in strict mode, so type and template errors are build failures. **Paraglide** rather than a runtime translation library, because it compiles each phrase into a function — a misspelled key is a build error instead of a blank button in a kitchen. **Tailwind 4** rather than hand-written CSS, because its vocabulary is fixed: an agent cannot quietly invent a fifteenth shade of grey, and CSS nobody ever reads does not rot into near-duplicate rules.

## Considered options

- **React 19 + Vite + TypeScript.** The benchmark favourite, the larger ecosystem, and the higher floor. Rejected — but it was recommended twice during the session before the evidence above settled it, and it remains the correct fallback if Svelte proves unreliable in practice. Its ecosystem advantage is worth least here in any case: [#13](https://github.com/BatterWorks/Kamosu/issues/13) deliberately ruled out a borrowed design system, which is most of what that ecosystem offers.
- **Solid.** Smallest ecosystem of the three (~1.5M weekly downloads against React's ~190M), with none of Svelte's compensating first-party documentation for models. Rejected.
- **Svelte 5 + SvelteKit static + TypeScript + Tailwind 4 + Paraglide** (chosen).

## Consequences

- **Three guardrails are part of the decision, not optional hygiene.** Svelte's `llms-small.txt` is committed and named in `AGENTS.md` so every frontend session has current syntax in front of it; `llms-full.txt` is committed as a searchable lookup for what the small file omits, both pinned to a version and refreshed deliberately. `svelte-check` runs strict in the build. Frontend tests are non-negotiable — they are the only thing between a bad-day component and the kitchen. Removing any of these removes the reason Svelte was chosen over React.
- **Tailwind's own palette and spacing must be replaced wholesale, not extended.** Apps that ship Tailwind's defaults are the ones that look templated, which is the precise failure [#13](https://github.com/BatterWorks/Kamosu/issues/13) deferred the visual identity to avoid. Tailwind commits nothing about the look: tokens are exactly what the visual identity fills in later, so this does not reopen ADR 0011's "guessing twice" concern.
- **Tailwind's global classes are what keep the Share Link page from drifting.** Svelte's scoped styles generate machine names at build time, which cannot be reused by the Rust template that renders that page ([ADR 0013](./0013-offline-you-may-write-your-own-history-never-the-recipes.md)). Tailwind's classes are identical everywhere, so both renderings draw from one generated stylesheet — a build guarantee rather than a discipline someone must maintain. This is the one place Tailwind was chosen for a reason specific to Kamosu rather than a general one.
- **iOS is the platform to test against.** Every browser capability this frontend depends on — Wake Lock, View Transitions, service workers, storage that survives — landed later and more awkwardly in Safari than anywhere else. Designing for the iPhone covers Chrome and Android with room to spare; the reverse is not true.
