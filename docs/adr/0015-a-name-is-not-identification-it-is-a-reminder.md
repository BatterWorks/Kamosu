# A name is not identification, it is a reminder

A Version records the **Hand** of the Person who wrote it: their name together with a permanent id minted with their account. A Branch has an id of its own and records the Hand of the Kitchen writing it. Both travel in a share bundle, and **neither is ever verified**. Anyone who opens the file can put any Hand in it, Kamosu will display exactly what it was handed, and Kamosu says so plainly rather than implying a check it does not make.

_(Amended by [ADR 0041](./0041-a-recipe-is-written-in-a-cookbook-and-seen-in-a-kitchen.md): the Hand a Branch records is its **Cookbook**'s, not a Kitchen's, and the Cookbook's name is what labels the switch.)_

Attribution in Kamosu is a courtesy. It works because you already know who sent you the file — it is not introducing you to Marc, it is helping you remember which recipe is his.

## Why

- **The threat model is empty.** The realistic scenario is a friend emailing a recipe. Forging authorship requires editing a file by hand to claim credit for a lasagne, and anyone motivated enough could simply retype the recipe — the same reasoning that killed the read-only tier in [ADR 0007](./0007-a-recipe-is-held-by-a-kitchen-not-a-person.md).
- **The precedent is overwhelming.** Git has recorded its author as free text for twenty years across every serious software project on earth; `--author` accepts anything. Signing exists there and is used by a rounding error of projects, because "who wrote this line" almost never has an impostor behind it.
- **A check that fires sometimes teaches people it fires always.** This is the argument that decided the shape. There is exactly one claim Kamosu genuinely *could* contradict — Versions are append-only and never deleted ([ADR 0004](./0004-one-lineage-many-branches.md)), so a bundle bearing **your own** Hand on a Version you do not hold is provably false. Marking it was rejected anyway: someone who watches Kamosu catch one forgery reasonably concludes it catches forgeries, and then trusts every unmarked name in the library. Silence about all of it is honest; silence about all but one is a lie by implication.
- **A Hand is cheap and buys real things a bare name cannot.** Two friends called Marc stay two people. Renaming your account does not detach you from your own history. A returning bundle is recognisably the same correspondent. None of it requires a single cryptographic operation.

## Considered options

- **A display name and nothing else.** Rejected: too little for almost no saving. Without a stable id you cannot tell one Marc from another, and a rename either rewrites history or freezes a stale name into it forever.
- **Signatures — a key pair per Person, trust-on-first-use.** Rejected: real engineering against an adversary who does not exist, and it drags in key storage, backup and a lost-key failure that silently breaks a person's future history. The cost lands where it hurts most — "unverified" warnings inside a cookbook.
- **A name plus a permanent portable id, unverified** (chosen).

## Consequences

- **Authorship can never be part of a fingerprint, and neither can the note.** A Version is named by a fingerprint of **the recipe state alone**. Put the author in it and two people writing the identical recipe hold two different Versions, and the Branch Point stops being computable — the mechanism the whole map rests on. The same argument covers the *what changed* line: it is frozen once written but is no more part of a Version's identity than its name is, so one Version may reach two people carrying two different notes. One consequence reads oddly and is correct: a single Version can legitimately carry two authorship claims, because two people wrote the same thing.
- **On your own instance a name is a fact; off it, a name is a souvenir.** A Hand stores the id *and* the name as written, and the written copy is what travels. On screen, a Hand this instance minted resolves to that Person's **current** name, so renaming yourself reaches forty old Versions at once; a Hand from elsewhere shows the name that arrived. Where old bundles disagree about one remote Hand, the most recently received name wins. This fulfils [ADR 0007](./0007-a-recipe-is-held-by-a-kitchen-not-a-person.md)'s promise that leaving a Kitchen never erases you from history better than freezing the string did — the id is welded on whatever happens to the name.
- **A Branch has an id of its own and records its Kitchen's Hand.** Not identified *by* its Kitchen: [ADR 0006](./0006-a-translation-is-a-branch.md) makes a Translation a Branch of the same Lineage, so one Kitchen legitimately holds several Branches of one recipe. The Kitchen's Hand is what labels [ADR 0014](./0014-a-divergence-is-two-recipes-not-a-difference.md)'s divergence switch — *Chez Dupont*, which is what you actually recognise — and what makes a second bundle from the same friend that Branch continuing rather than a third one to line up beside the others.
- **The Branch carries the label; the Versions carry names.** A received Branch is headed by its Kitchen and its Versions read as ordinary names. No per-Version "imported" badge: that is the check-that-fires-sometimes mistake wearing different clothes. The Kitchen label is not a trust signal but a factual answer to a question the reader is about to have with their thumb — you cannot edit another Kitchen's Branch, you take a **Copy**. This also makes the odd-looking case read correctly: because a Lineage is shared, the early stretch of *your own* Branch legitimately carries someone else's name, which is [ADR 0004](./0004-one-lineage-many-branches.md) working as intended and must not look like an error.
- **An agent is recorded, locally, and never travels.** [ADR 0007](./0007-a-recipe-is-held-by-a-kitchen-not-a-person.md) left this input here. A Version records which Access Key wrote it, visible on your own Thread as *"Marc, via `kitchen-laptop`"*, and stripped from every bundle — because [ADR 0006](./0006-a-translation-is-a-branch.md) already settled that an agent under your Credential is a scribe and you are the author, because a Key's name is a fact about your own plumbing that leaks nothing useful, and because publishing it would function as a scarlet letter with no action attached. What it buys is the question that immediately follows revoking a Key: **revocation never rewrites history**, but you can now find everything that Key wrote and decide, recipe by recipe, whether to write a corrected Version over it.
- **Credit is written down, never wired up.** [ADR 0014](./0014-a-divergence-is-two-recipes-not-a-difference.md) already makes a change carried across an ordinary Version of your own. Kamosu pre-fills the *what changed* box — *"Took the marinade step from Chez Dupont"* — editable and deletable, ordinary text, no new stored shape. A structured "taken from" pointer was rejected: it references another Branch's Version and rots the moment that bundle is not held, and it invites the reading [ADR 0014](./0014-a-divergence-is-two-recipes-not-a-difference.md) fought off, that carrying a change across is a partial merge leaving a machine-readable trail.
- **v1 signs nothing, and [#17](https://github.com/BatterWorks/Kamosu/issues/17) leaves the room.** Signatures are stored shape under [ADR 0009](./0009-the-v1-cut-line-is-drawn-at-shape-not-at-features.md), so retrofitting them means a library with a permanent unsigned era in it. The bundle format keeps a signature slot so the decision stays reversible, and [#17](https://github.com/BatterWorks/Kamosu/issues/17) owns it.
- **This is the seed cross-instance Kitchens would need.** A shared Kitchen spanning two servers is **refused, not deferred** — two servers writing to one Branch is a merge, which [ADR 0004](./0004-one-lineage-many-branches.md) rules out. What is deferred is remote membership (a client logged into two instances) and subscription (bundles arriving on a timer), both of which hold never-merge intact and both of which need exactly one thing: a way to say *this is the same Marc* across two machines. The Hand is that, decided here for other reasons.
