# A Secret is spent or revoked, never on a clock

_(Amended by [#171](https://github.com/BatterWorks/Kamosu/issues/171), 2026-09-26: a **Share Link** keeps its Secret readable, so the share screen shows its address for as long as it lives. Every other Secret stays hashed and shown once. See "A Share Link's address stays readable" below.)_

_(Amended by [#373](https://github.com/BatterWorks/Kamosu/issues/373), 2026-10-19: a count of wrong passwords is forgotten an hour after its last, at every name alike. The password is not a Secret, so the title's rule is untouched.)_

_(Amended by [ADR 0054](./0054-a-phone-shares-into-kamosu-through-one-operation-and-an-add-only-key.md), 2026-10-24: an **Add-only key** is a kind of Access Key chosen at minting that may call only a short list of Operations, decided once per declaration as a Job Key's are. That is not the scoping turned down in "A leaked Key is answered by visibility": it puts no wall in front of any Operation.)_

Kamosu has one kind of secret and one rule for it. A **Secret** is a long random string where holding it *is* the permission — the **Share Link** token, the **Access Key**, the **Invite**, the recovery link, and the **Session** a browser holds after logging in. Every one is **256 bits from the operating system's random source, stored hashed, revocable on its own, and never on a clock**, save that a Share Link is also kept readable (#171, below). A Secret ends one of exactly two ways: it is **spent** (an Invite and a recovery link die on first use) or it is **revoked** (you turn it off). Time never kills one.

The password is the sole exception, and it is not a Secret: it is short, human-chosen, and never stored — only an **Argon2id** hash of it is, tuned to roughly a tenth of a second and ~20 MB per check. Argon2id salts every password separately and stores the salt inside the hash; that is automatic and is recorded here so it is not later mistaken for an oversight.

- **A Session is a Secret.** Logging in mints one, carried in a cookie that is `HttpOnly`, `Secure` and `SameSite=Lax`. The cookie lasts 400 days, the most a browser allows, and every request it is accepted for sets it again with a fresh 400 days (#137). Without that it would be a browser-session cookie, which a phone throws away whenever it closes the app, and the Session would outlive the only device holding it. So the promise covers the browser too: a device opened at least once every 400 days stays signed in until the Session is revoked. It appears in a list beside the Person's Access Keys — *iPhone, last used 2 hours ago* — and is ended from any device.
- **An Access Key acts as the Person**, across every Kitchen they cook in. It cannot mint another Key, change the password, or mint an Invite: an agent cannot turn a leak into an account.
- **A Secret is shown once**, at minting, and is otherwise known only by its name and when it was last used. The Share Link is the one exception, below.
- **A Share Link's address stays readable** (#171). Its Secret is kept beside the hash, and the share screen shows the address, with Copy and Open, for as long as the link is live. A visitor is still looked up by the hash alone. A link minted before #171 kept only its hash, so it goes on opening but its address cannot be shown; the screen says so, and ending it and sharing again mints one that can. The URL is built against the public address stored now, so after `set_public_address` the screen shows the new address. That is intended: the new address is the one that opens, and the instance serves the same Secret at either.
- **Kamosu throttles where the secret is human-chosen, and nowhere else.** A wrong password makes the *next* attempt on that account name wait — nothing, nothing, 1s, 2, 4, 8, 16, capped at 30 — and a correct password clears the counter instantly. A counter is also forgotten an hour after its last wrong password (#373), at every name alike, so made-up names a stranger tries are not kept for good. Forgetting those alone would say which names are real, and forgetting a real one costs nothing, since a guesser who waits an hour between tries is slower than the thirty-second wait already holds them. Nothing else is throttled.
- **The wait holds nothing, and one try per name is checked at a time** (#138). An attempt that arrives while its name is waiting, or while another attempt at it is being checked, is refused at once as *busy* with the seconds left, and the sign-in screen counts them down. Until #138 the wait was a sleep on a request thread: attempts sent together all slept and were then all checked, and four of them froze the instance for everyone for thirty seconds.
- **Password work runs beside the requests, two at a time.** Hashing and checking move off the threads that answer requests, behind a cap of two. A sign-in that finds both busy waits its turn in a line of 32, since two people signing in at once is ordinary; one that finds the line full too is refused as busy. A name nobody holds is checked against a stand-in hash made the same way, so it costs what a real one does.
- **A new password is at least 15 characters** (#138), the figure NIST SP 800-63B-4 sets for a password that is the only factor. There are no composition rules and no maximum below 64. It is checked where a password is set, never at login, so one set before the minimum keeps working. A space at either end is no part of a password (#140): it is trimmed where one is set and at login alike, so a passphrase chosen or pasted with a stray space signs in whichever way it is typed. NIST allows a verifier to normalise a password as long as it does so the same way every time.

## Why

- **Expiry is a wall Kamosu cannot build.** [ADR 0018](./0018-a-share-begins-at-the-beginning-and-there-is-no-unsay.md) already established there is no unsay: ending a Share Link "reaches no copy already sent." A clock on one would be exactly that pretence. The same runs down the list — a 90-day Access Key does not protect a Key that leaked on day 3; it annoys you on day 90. **Spent-or-revoked is a real defence; a clock is theatre**, and this house does not ship walls it cannot build.
- **The clock would fire on the household, not on an attacker.** [ADR 0013](./0013-offline-you-may-write-your-own-history-never-the-recipes.md) makes the installed app work with no server at all, so a session expiry is not discovered at a laptop — it is discovered by a phone that has been offline for a fortnight, at the stove, when the thing needed is a recipe already on the device.
- **A lockout is a weapon handed to the attacker.** Freezing an account after N failures means anyone who knows an account name can lock the household out of its own cookbook, for free, without ever guessing right. That is a worse outcome than the attack it prevents. Slowing the door has no state a stranger can push you into that the correct password does not clear in one keystroke once the wait is over.
- **Refusing during the wait is a narrower lockout, accepted on purpose** (#138). A wait that never refuses has to let every attempt through eventually, and attempts sent together then all get checked, so it limits nothing: the "no throttling at all" rejected below, in practice. Refusing instead means someone hammering one exact name keeps that name's sign-in refused for as long as they keep at it. That is bounded in a way the lockout above is not: it lasts only while they keep sending, never past thirty seconds after they stop, touches no device already signed in (Sessions never expire), and a recovery link from an Operator goes round it. The cap on password work has the same shape across names: a crowd of tries at made-up names can fill the line and have every login refused while it lasts, which is latency and refusal at the login page and never at anything else ([ADR 0032](./0032-a-stranger-may-cause-work-never-work-that-scales-with-them.md)'s bargain). Both are named in [ADR 0034](./0034-kamosu-names-what-it-does-not-defend.md)'s list.
- **Counting per account name rather than per address sidesteps the proxy entirely.** Behind a reverse proxy ([ADR 0028](./0028-kamosu-is-one-file-and-one-directory.md)) every request arrives looking like the proxy, and the visitor's real address survives only in a header the visitor can forge — so a per-address limit is either useless or bypassable. The account is the thing being attacked and is therefore the right unit. The same delay applies to names that do not exist, and so does the same work: a name nobody holds is checked against a stand-in hash, so neither the wait nor the time a refusal takes answers *who has an account here*. A Share Link page prints its sharer's name, which is the sign-in name, so this protects against a scanner, not against someone holding a link.
- **256 bits makes enumeration impossible, not merely slow**, which is why nothing but the password is throttled. Rate-limiting Share Link lookups would defend a door with no handle while implying the entropy was not enough.
- **A Share Link grants less than a hash is worth** (#171). It can read one recipe. It cannot act as anyone, change anything or mint anything. Hashing a Secret helps only when the database is stolen, and whoever holds Kamosu's database holds every recipe a link could open, since [ADR 0028](./0028-kamosu-is-one-file-and-one-directory.md) keeps everything in one directory. So the hash protected nothing a link grants, and it cost the owner something real. To send the recipe to a second person they had to end the link and mint a new one, which breaks every copy already sent: the harm [ADR 0018](./0018-a-share-begins-at-the-beginning-and-there-is-no-unsay.md) says the owner should control. Access Keys, Sessions, Invites and recovery links keep the old rule, because each acts as a Person or makes an account, and a readable copy of one in the database would be a real leak.
- **Two things that look alike are kept apart.** A Session and an Access Key share a shape but not their powers: a Key is minted deliberately for an agent, may be read-only, and can mint nothing; a Session belongs to a person who typed a password and has that person's full powers. The glossary's rule that a **Credential** comes from one of two places stays true.
- **A leaked Key is answered by visibility, not by restriction.** Scoping a Key to one Kitchen would be a wall to explain at every Operation, against a model where a Person cooking in several Kitchens is one fact about them. A name and a last-used time make an unused Key visible, which is the failure this actually has.

## Considered options

- **A rule per secret** — Invites expiring in 7 days, recovery links in 15 minutes, Keys renewed at 90 days, Sessions at 30. Rejected: five policies to explain and get wrong, in a project that has repeatedly collapsed scales ([ADR 0026](./0026-a-recipe-is-seen-by-its-kitchen-or-by-anyone-with-the-link.md), [ADR 0022](./0022-doubt-makes-a-new-food-never-a-merge.md)), and each of the five defends less than it appears to.
- **Account lockout after N failed passwords.** Rejected above: a free denial of service against the household.
- **Waiting without ever refusing** (#138's option B). Rejected: attempts sent together all get checked after the wait, so the throttle stops limiting guesses.
- **Refusing, but letting a browser that has signed in as that name before skip the refusal** (OWASP's device cookie, #138's option C). Rejected for now: it closes the narrow lockout only for a returning device, which is rare here because Sessions never expire.
- **No throttling at all**, relying on Argon2id's tenth of a second. Rejected as thin rather than wrong: it still permits ~850,000 guesses a day against a box that is on the open internet by design.
- **A Session *is* an Access Key**, minted automatically and named for the device. Rejected: it collapses two things with genuinely different powers.
- **Re-minting a Share Link silently whenever its address is asked for** (#171). Rejected: it would break every address already sent, which is the harm the amendment exists to stop. A link minted before #171 is left alone, and the screen says why it shows no address.
- **Scoping an Access Key to a Kitchen.** Rejected: a wall against the grain of [ADR 0007](./0007-a-recipe-is-held-by-a-kitchen-not-a-person.md).
- **A pepper** — one secret mixed into every password and kept outside the database. Rejected: it defends the case where the database is stolen without the filesystem, which [ADR 0028](./0028-kamosu-is-one-file-and-one-directory.md) makes impossible by putting everything in one directory. In `/data` it is stolen alongside the database; as an environment variable it breaks [#27](https://github.com/BatterWorks/Kamosu/issues/27)'s rule that no environment variable is required at all, and losing it kills every password in the house — a new way to brick an install, in an app whose packaging exists to remove those. A pepper on the same disk is a wall contradicting the glossary's own sentence that whoever holds the disk holds everything.

## Consequences

- **An Invite you sent and forgot stays live until you revoke it.** Accepted, and answered by showing the live ones rather than by a timer.
- **A stolen unlocked phone is a logged-in phone.** The answer is ending that session from another device — immediate, rather than up to thirty days late. Recorded in [ADR 0034](./0034-kamosu-names-what-it-does-not-defend.md).
- **Six wrong passwords in a row means the seventh waits 16 seconds.** That is the whole penalty, and it is gone the moment you get it right.
- **Every Secret must be generated from a cryptographic source, never a general-purpose random number generator.** One lapse is indistinguishable from correct behaviour until someone exploits it.
- **The Sessions-and-Keys list is a v1 screen**, not a nicety: revocation is the only answer this ADR gives to every loss, so it has to exist and be reachable.
