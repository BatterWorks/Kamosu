# A refusal answers as if the thing were not here

Where Kamosu **worked a Kitchen out** from an id the caller named, a Person who does not cook in that Kitchen is refused with the answer they would have got had the thing they named never existed here. Word for word, status for status.

_(Amended by [ADR 0041](./0041-a-recipe-is-written-in-a-cookbook-and-seen-in-a-kitchen.md): Kitchen membership is no longer the one check. There are two, *may change* (a Co-author of the recipe's Cookbook) and *may see* (a member of a Kitchen the Cookbook is in), and the rule below governs both.)_

- **The caller named the Kitchen** — `create_recipe` with a `kitchen_id`, and most of the membership checks in the Core — keeps the plain refusal: *this Person does not cook in this Kitchen*. Being told you do not cook in a Kitchen whose id you just supplied tells you nothing you did not already know.
- **Kamosu worked the Kitchen out** — from a Branch, a Tag, an Import, a shopping-list row, a Thread — answers *no such Branch*, *no such Tag*, *no such Import*: the very sentence the absent case raises, from the very function that raises it.
- **A Job follows the same rule**, and so do a Sheet and an Attempt. A Job belonging to another Person answers exactly as a Job id naming nothing does. `/api/sheets/<id>` resolved a *Sheet* id, so it answers *no Sheet with that id* in both cases — saying *no Job with id* there would itself have told the caller their id names somebody's Job. An Attempt that is not yours answers *no such Attempt*, which is what an id naming nothing answers.

The two checks are separate functions, `ensure_member` and `ensure_member_or_absent`, so which group a call site is in is readable where the call is, without tracing where the Kitchen came from. The second takes the refusal to raise as an argument, and that argument is the same `no_such_branch`, `no_such_tag`, `no_such_import`, `no_such_sheet`, `no_such_attempt` the not-found path calls. Identical text is the whole mechanism, and one source for that text is what keeps the two identical as either gets edited.

## Why

- **The refusal was the answer to a question the asker could not otherwise ask.** A Branch held by another household answered `401`; a Branch id this instance never held answered `404`. Neither handed over the recipe, but the difference between them told the caller that some other household here holds that recipe ([#97](https://github.com/BatterWorks/Kamosu/issues/97)). Branch ids are random, so nobody can sweep the library — but a **Bundle hands you one**, which is exactly how this was found.
- **The check was never in the wrong place; its refusal was the wrong word.** Authorisation happens once, in the Core, exactly as [ADR 0001](./0001-both-doors-generated-from-one-operation-catalogue.md) requires. The leak was that the check runs *after* the Branch row has been resolved to a Kitchen, and raised a different kind of error than the missing row did.
- **Kamosu had already decided this question once and could not keep the answer.** The MCP Door collapsed a forbidden Job and an absent one into one answer, with a comment saying that asking must tell you nothing about other People's work. That collapse lived **inside a Door**, so it never reached the web Door, where `get_job` went on answering `401` against `404`. By ADR 0001's own rule a decision in a Door is in the wrong place, and this is the proof: it did not travel. The rule now lives in the Core, and both `tasks/get` and `tasks/cancel` have stopped hand-rolling it.
- **This was cheap and narrow next to the rest of [ADR 0034](./0034-kamosu-names-what-it-does-not-defend.md)'s list.** That list is mostly things Kamosu genuinely cannot fix — an unverified Hand, an agent that believes what it reads, a stolen unlocked phone. Naming a gap you could close in an afternoon reads differently from naming one you cannot close at all, and it would make the rest of the list weaker by association.

## Considered options

- **Name it in ADR 0034's list instead of closing it**, in the voice that list uses: *on an instance with more than one household, someone holding a recipe's Branch id can tell whether another household here holds that recipe.* Rejected for the reason above — but it was a real option, and it is the option every wall Kamosu decided not to build took. ADR 0034 exists precisely so that answer is available and honest.
- **Translate every `Unauthorized` to a not-found at dispatch**, once, for every Operation. Rejected: a wrong password must still say so, a spent Invite must still say so, and a Kitchen the caller named must still get the membership refusal. The choice belongs at each site where Kamosu did the looking up, which is why it is a second function rather than a blanket rule.
- **Invent a new, careful sentence for the derived case.** Rejected: a distinct sentence is a distinct answer. Hedged wording would leak the same fact more politely.

## Consequences

- **This closes the answer and not the clock.** A non-member's request still does one more indexed lookup — the membership query — than an absent id's does before refusing, so the distinction survives in timing. That is accepted. Constant-time refusals would put a constraint on twenty-odd functions that someone would break without noticing, and the fact being protected is whether a neighbouring household holds a pizza recipe.
- **Nothing is added to ADR 0034's list, and nothing to the README.** The leak is closed rather than named, and the timing residue is not something an Operator can act on. That list is for the things they can.
- **This rule closes what a refusal says, and refusals are not the only thing that answers.** `save_recipe_version` against another household's Branch does not refuse at all: it makes a Copy, by design ([#54](https://github.com/BatterWorks/Kamosu/issues/54), [ADR 0025](./0025-an-imported-recipe-is-an-ordinary-recipe.md)), and a Copy carries the source's chain verbatim ([#82](https://github.com/BatterWorks/Kamosu/issues/82)) — so reading the Copy reads the source's Versions. That is a larger hole than the one closed here and a different one: it is not a refusal returning the wrong word but a feature handing over content, and deciding what a Copy should do for a non-member reopens ADR 0025. It was filed as [#100](https://github.com/BatterWorks/Kamosu/issues/100) rather than fixed here, and #100 closed it by refusing: **a Copy starts only from a Branch a Kitchen of yours holds.** A save onto any other Branch answers *no such Branch*, under this rule, before anything reads the Branch. That cost nothing legitimate, because a received Bundle and a kept Share Link both put the Branch in the receiver's own Kitchen before anyone changes it. `promote_attempt_photograph` and `promote_as_cooked` reached a Branch the same way and are closed the same way, with the check made before the Lineage comparison. Otherwise *that Branch is not a Branch of the recipe this Attempt cooked* would itself say that the Branch exists.
- **A new Operation that resolves an id to a Kitchen has to choose.** Reaching for `ensure_member` where the Kitchen was worked out reopens the leak, and nothing but reading the call site will say so. The sweep in `tests/defences.rs` asks every Operation that refuses on a worked-out Kitchen, `branch_point` included — which names neither of its ids `branch_id` and is the one such Operation easiest to write and forget. An Operation added to that sweep is caught; one left off it is not.
- **Some refusals got less helpful, and that is the trade.** A member of one Kitchen who names a Tag belonging to a Kitchen they do **not** cook in is now told the Tag does not exist. Where they cook in both, they still get the sentence saying what actually went wrong — `merge_tags` checks both Tags before comparing their Kitchens for exactly that reason.
- **This rule is about Kitchen membership, Job ownership and Attempt ownership, and nothing else.** A spent Invite, a revoked Secret and a wrong password say what they say for reasons recorded elsewhere.
- **An Attempt is covered even though nobody is handed an Attempt id.** Unlike a Branch id, which travels in a Bundle, an Attempt id is minted by the client that cooks and given to no one — so the argument for closing it is weaker than for a Branch, and the case was first left open on exactly that reasoning. It is closed anyway, because the reasoning is about how hard the leak is to reach rather than about whether it is one, and because the whole point of writing the rule down is that the next person should not have to redo that judgement per id. All eight Operations that reach an Attempt go through one gate, `attempt_state_owned_by`, so this cost one line. The strongest case is the one the behaviour suite asserts: a Person who cooks in the same Kitchen may read the recipe and still learns nothing about whether somebody is cooking it.
- **One Attempt path is left saying an id is in use, and it has to.** `start_attempt` accepts a client-minted `attempt_id` so that a phone which never heard the answer can send the same start twice. Sent an id that is *yours*, it hands back your cooking; sent one that is somebody else's, it refuses with *that attempt_id is taken*. That still says the id exists. There is no honest alternative: the caller is asking to create a row at that id, and a free id succeeds, so no wording makes the two outcomes alike. It discloses less than the refusal this ADR removed — that an id is in use, not whose — and closing it would mean either silently minting a different id than the client asked for, which breaks the retry that the parameter exists to serve, or dropping the parameter and with it the retry.
