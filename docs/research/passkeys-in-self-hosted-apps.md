# Passkeys and changing your own password in other self-hosted apps

Research date: 2026-10-19. Asked for issue #370, which adds passkeys as a way to sign in and lets a signed-in person change their own password. The issue asks for prior art before its three visible surfaces are designed: the sign-in screen, the passkey list in Settings, and the change-password sheet.

Five apps were read in their own source code, at the commits named in each section: Immich, Vaultwarden with the Bitwarden web vault it serves, Nextcloud, Gitea and authentik. Then the Rust crates, the browser side, and the W3C specification. Nothing was built or run. Every claim carries a confidence mark. **High** means read in source, in a registry's API answer, or in the specification. **Medium** means first-party documentation. **Not found** means I looked and saw nothing. Source references are `repo:path:line` against the commit named in the section.

## Summary

- **Every app that signs people in with a passkey asks for no name first, except Nextcloud.** Immich (in an open pull request), the Bitwarden web vault and Gitea send an empty `allowCredentials` and let the browser offer whatever passkeys it holds for the site. Nextcloud asks for the login name, then lists that account's credentials (High).
- **The passkey button sits below or beside the password form, never in place of it.** Immich puts "Login with passkey" under the password form after an "or" divider. Bitwarden puts "Log in with passkey" under the email step's Continue button, after "or". Nextcloud and Gitea use a quieter link under the form (High).
- **Only authentik uses passkey autofill** (conditional mediation, `autocomplete="username webauthn"`). Immich, Bitwarden, Nextcloud and Gitea call the browser only when the button is pressed (High).
- **Each passkey gets a name in every app, and the apps differ on where it comes from.** Typed before creating it (Nextcloud, Gitea), typed after (Bitwarden), or filled from the authenticator's AAGUID and renamable (Immich, authentik) (High).
- **Re-entering the password to add a passkey splits the field.** Bitwarden and Nextcloud ask for it. Immich and Gitea do not (High).
- **The relying party ID comes from one of two places.** A configured public URL (Vaultwarden's `DOMAIN`, Bitwarden's vault URL, Gitea's `ROOT_URL` domain, Immich's optional "Passkey domain"), or the request's own `Host` or `Origin` (Nextcloud, authentik, Immich by default). Immich's setting is the only one that warns, in its own words, that changing it ends existing passkeys (High).
- **Over plain HTTP, the apps that say anything say it plainly.** Nextcloud shows "Your connection is not secure. Passwordless authentication is only available over a secure connection." Gitea has "WebAuthn only supports secure connections." Immich and Bitwarden hide the button, because the browser hides the API (High).
- **Changing a password asks for the current one everywhere, and the apps disagree on everything after that.** A confirm field: Immich, Bitwarden and Gitea have one, Nextcloud does not. Other sessions: Immich shows a switch, off by default (and, at the commit read, ends them whatever it says). Bitwarden and Vaultwarden end them all and say so. Gitea deletes remember-me tokens without saying so. Nextcloud ends other sessions that stored the old password within five minutes, without a word (High).
- **`webauthn-rs` is the maintained Rust server crate, and its stable 0.5.5 links OpenSSL.** The 0.6.1-dev prerelease has dropped OpenSSL for pure-Rust cryptography, and its maintainers wrote in September 2026 that a stable release is "close". `passkey-rs` from 1Password is a client and authenticator, not a server library (High).
- **The browser's own JSON helpers are Baseline 2025.** `PublicKeyCredential.parseCreationOptionsFromJSON`, `parseRequestOptionsFromJSON` and `toJSON` shipped in Chrome 129, Firefox 119 and Safari 18.4 (High). Immich and Nextcloud use `@simplewebauthn/browser` instead. Gitea and Bitwarden call `navigator.credentials` directly.

## What stays unverified

- Immich's passkeys are an open pull request (#32194, by a member of the Immich organisation, opened 2026-10-07, not a draft). What ships may differ.
- Vaultwarden's passkey sign-in is in four open pull requests and none is merged. Vaultwarden today hides the Bitwarden passkey screens with CSS.
- How each app looks on screen. I read templates and components, and took no pictures.
- Whether `gcr.io/distroless/cc-debian13`, Kamosu's runtime image, carries `libssl`. That matters only if `webauthn-rs` 0.5.5 is linked dynamically.
- Home Assistant, Mealie and Tandoor were checked and dropped. Home Assistant core has no WebAuthn code. Mealie's only hit is in its OIDC documentation. Tandoor ships generated client files for django-allauth's WebAuthn API (`vue3/src/authapi/apis/AccountWebAuthnApi.ts`) but no screen and no `MFA_` setting was found. All three are Not found for passkey sign-in.

## Immich

Source: github.com/immich-app/immich `main` at `53618ff7496ee313d1cff7b3bcdf19c82b765cdf` (2026-10-17) for the password change. Passkeys are in pull request [#32194](https://github.com/immich-app/immich/pull/32194) "feat: passkeys" at head `d0407bacb7b1f04dcfb21835fe7b5e6c2c9e8bdd` (updated 2026-10-15, open). The PR uses `@simplewebauthn/server` 14.0.3 and `@simplewebauthn/browser` 14.0.0 (`server/package.json:66`, `web/package.json:39`).

1. **Sign-in screen.** The email and password form comes first, then a divider, then a full-width "Login with passkey" button, then OAuth (`web/src/routes/auth/login/+page.svelte:176-206`). The button is the secondary colour when password sign-in is on and the primary colour when it is off (`:202`). It is shown only when the server has passkeys on and `browserSupportsWebAuthn()` is true (`:31-35`). The flow is username-less: the server's authentication options carry no `allowCredentials` and `userVerification: 'required'` (`server/src/services/passkey.service.ts:133-151`), and the account is found from the credential ID, cross-checked against the `userHandle` (`:162-168`). No conditional mediation: the email field is `autocomplete="email"` with no `webauthn` token (`+page.svelte:177`), and `startAuthentication` is called without `useBrowserAutofill` (`web/src/lib/services/passkey.service.ts:86-90`). A cancelled browser prompt (`NotAllowedError`) shows no error (`passkey.service.ts:28`, `+page.svelte:127`) (High).
2. **Enrolment.** A "Passkeys" section in the user settings list, shown when passkeys are on (`web/src/routes/(user)/user-settings/UserSettingsList.svelte` in the PR diff). A "New passkey" button sits above a table with the columns Name, Created, Last used ("Never" when unused) and Action (`UserPasskeyList.svelte:39-78`). The server stores `name`, `createdAt`, `usedAt`, `counter`, `transports`, `backedUp` and `deviceType` per passkey (`server/src/schema/tables/passkey.table.ts`). Naming: a name sent with the request, else the authenticator's name looked up from its AAGUID in the `aaguids` package, else the device and operating system read from the request ("… on …"), else "Passkey" (`passkey.service.ts:115-121`). Right after creation a small form opens with the name filled in, to rename it (`web/src/lib/services/passkey.service.ts:40-43`, `web/src/lib/modals/PasskeyUpdateModal.svelte`). Removal asks "Are you sure you want to delete this passkey?" and then shows "Removed passkey: {name}" (`passkey.service.ts:105-121`; `i18n/en.json`). Adding one asks for no password: the server only checks that the caller holds a session, not an API key (`passkey.service.ts:47-49, 234-238`) (High).
3. **HTTPS and the relying party.** The RP ID is the hostname of the request's `Origin` header unless an administrator sets "Passkey domain". The setting's description reads: "Domain used for passkeys (relying party). Leave blank to infer from the origin header. Changing this value will result in existing passkeys no longer working." (`passkey.service.ts:269-296`; `i18n/en.json`, `passkey_domain_description`). With a domain set, any other origin is refused ("Origin is not trusted"), except up to five "Additional domains" published at `/.well-known/webauthn` as related origins (PR description; `passkey.service.ts:240-249, 290-293`). Nothing names HTTP. Over HTTP the browser hides `PublicKeyCredential`, so the sign-in button does not appear, and "New passkey" shows "Passkeys are not supported by this browser" (`passkey.service.ts:35-38`) (High).
4. **Changing the password.** An account settings section headed "Password" with Password, New password and Confirm password fields, and a switch "Log Out All Devices" described as "It is recommended to log out of all other devices". The switch is off by default, and Save stays disabled until both new fields match (`web/src/routes/(user)/user-settings/ChangePasswordSettings.svelte:7-48`; `i18n/en.json:1340`). The server checks the current password and requires at least 8 characters (`server/src/dtos/auth.dto.ts:70-76`; `server/src/services/auth.service.ts:137-159`). **At this commit the switch has no effect.** `onAuthChangePassword` ends every other session whatever `invalidateSessions` says (`server/src/services/session.service.ts:84-87`). The switch came from PR #23188 (merged 2025-10-27), which answered issue #19620, "Password change does not logout open sessions" (High, read in source and not run).
5. **Limits and settings.** No limit on the number of passkeys found. Registration: `residentKey: 'required'`, `userVerification: 'required'`, `attestationType: 'none'`, existing credentials excluded (`passkey.service.ts:54-63`). A challenge is kept in an `auth_challenge` table for 5 minutes and used once; a background job deletes expired ones (`:31, 65-70, 89-96, 251-258`). Passkeys are on by default (`config.passkey.enabled: true`) (High).

## Vaultwarden, and the Bitwarden web vault it serves

Sources: github.com/dani-garcia/vaultwarden at `58a980f850464f7d9cdc99a765df36f0a3308b91` (2026-10-16). github.com/bitwarden/clients at `abccf1e342dccba06a3cc635cd4c706defa64a32` (2026-10-19). github.com/bitwarden/server at `9129efbd1531d5d8472345638efad7ef25a7337a` (2026-10-16).

**Vaultwarden does not offer passkey sign-in today.** Its stylesheet hides the web vault's "Log in with passkey" settings and the button on the sign-in page (`src/static/templates/scss/vaultwarden.scss.hbs:51-58`). `GET /api/webauthn` returns an empty list "to prevent a 404", with the comment "used when login with passkeys is enabled, which Vaultwarden does not (yet) support" (`src/api/core/mod.rs:198-207`). Four open pull requests add it: [#5929](https://github.com/dani-garcia/vaultwarden/pull/5929) (opened 2025-06-04), [#7370](https://github.com/dani-garcia/vaultwarden/pull/7370), [#7784](https://github.com/dani-garcia/vaultwarden/pull/7784), and the consolidated #7297, which was closed. A commenter on #5929 called it "clearly the furthest-along implementation" (High). WebAuthn exists in Vaultwarden only as a second factor (below).

So for questions 1, 2 and 5, the answers below describe Bitwarden's own web vault against Bitwarden's own server. That is the screen a Vaultwarden user would get once one of those pull requests merges.

1. **Sign-in screen (Bitwarden).** The first step asks only for the email, with a Continue button. Below it are "or", a secondary "Log in with passkey" button, then single sign-on (`libs/auth/src/angular/login/login.component.html:1-65`). The flow is username-less: the server's assertion options carry `AllowedCredentials = Array.Empty` and `UserVerification = Required` (`bitwarden/server:src/Core/Auth/UserFeatures/WebAuthnLogin/Implementations/GetWebAuthnLoginCredentialAssertionOptionsCommand.cs:15-20`). No conditional mediation: the email input has no `autocomplete` attribute (`login.component.html:6-14`), and the login service passes no `mediation` (High).
2. **Enrolment (Bitwarden).** Under Settings → Security → Master password, below the change-password form (`apps/web/src/app/auth/settings/security/password-settings/password-settings.component.html`). The section is headed "Log in with passkey" with an On or Off badge. Each row shows the name, the encryption status ("Used for encryption", "Set up encryption", or "Encryption not supported") and "Remove". There is no date (`webauthn-login-settings.component.html`). Adding one runs in a dialog: first the master password or a one-time code (`app-user-verification`), then the browser prompt with "Keep this window open and follow prompts from your browser.", then "Passkey successfully created" with a Name field (50 characters at most) and the line "Name your passkey to help you identify it." (`create-credential-dialog/create-credential-dialog.component.html`, `.ts:37`; `apps/web/src/locales/en/messages.json`). Removing one is a dialog titled "Remove passkey" with the passkey's name, the warning "If all passkeys are removed, you will be unable to log into new devices without your master password.", and the master password again (`delete-credential-dialog.component.html`). Bitwarden's help page gives the same steps (https://bitwarden.com/help/login-with-passkeys/, Medium) (High).
3. **HTTPS and the relying party.** Bitwarden's server takes the RP ID from the host of its configured vault URL (`options.ServerDomain = new Uri(globalSettings.BaseServiceUri.Vault).Host`, `bitwarden/server:src/SharedWeb/Utilities/ServiceCollectionExtensions.cs:631-643`). Vaultwarden does the same for its WebAuthn second factor from the `DOMAIN` setting (`src/api/core/two_factor/webauthn.rs:35-47`). Its `.env.template` says "The domain must match the address from where you access the server … For U2F to work, the server must use HTTPS" (`.env.template:195-211`). The admin page's diagnostics show a "No Match" badge, "The domain variable does not match the browser location … Some features may not work as expected!", and a "No HTTPS" badge (`src/static/templates/admin/diagnostics.hbs:192-193`, plus the domain check). Those badges are for the Operator, not for the person signing in (High).
4. **Changing the password.** Bitwarden: Current master password, New master password, Confirm new master password, an optional hint, "Check known data breaches for this password", and "Also rotate my account's encryption key" (`libs/auth/src/angular/input-password/input-password.component.html:18-154`). Above the form a warning reads: "After changing your password, you will need to log in with your new password. Active sessions on other devices will be logged out within one hour." There is no choice. The client logs itself out after a change (`libs/angular/src/auth/password-management/change-password/change-password.component.ts`, `logoutService.logout(this.userId, "passwordChanged")`). Vaultwarden, behind the same screen, checks the current password, resets the security stamp and rotates every device's refresh token, then pushes a logout to every device except the one that made the change (`src/api/core/accounts.rs:634-685`; `src/db/models/user.rs:226-230`) (High).
5. **Limits and settings (Bitwarden).** Five passkeys per account (`WebauthnLoginAdminService.MaxCredentialCount = 5`, `apps/web/src/app/auth/core/services/webauthn-login/webauthn-login-admin.service.ts:43`). At five, the list says "Passkey limit reached. Remove a passkey to add another." Registration: `RequireResidentKey = true`, `UserVerification = Required`, `AttestationConveyancePreference.None`, existing credentials excluded (`GetWebAuthnLoginCredentialCreateOptionsCommand.cs`). The options go to the browser inside a signed token that lives 17 minutes, and a challenge cache makes each assertion challenge usable once (`WebAuthnLoginAssertionOptionsTokenable.cs:10-14`, `IWebAuthnChallengeCacheProvider.cs`) (High).

**Vaultwarden's second factor**, for the crate section: `webauthn-rs` 0.5.5 with the features `danger-allow-state-serialisation` and `danger-credential-internals` (`Cargo.toml:154-159`). It calls `start_passkey_registration`, then edits the result to make it act like a security key: user verification "discouraged" and extensions cleared. The registration state goes as JSON into a `twofactor` row (`src/api/core/two_factor/webauthn.rs:156-176, 281-289`). It links OpenSSL 0.10.81, with an optional `vendored_openssl` feature (`Cargo.toml:36-37, 225`) (High).

## Nextcloud

Source: github.com/nextcloud/server `master` at `4407a465999ea29d33663cac7ed83790ed63e1bf` (2026-10-19). WebAuthn through `web-auth/webauthn-lib` ^4.9.1 (`composer.json:74`). The browser half uses `@simplewebauthn/browser`.

1. **Sign-in screen.** Under the name and password form is a tertiary button, "Log in with a device", then "Forgot password?" (`core/src/views/Login.vue:69-95`). It swaps the form for a second one titled "Log in with a device", with a "Login or email" field and a "Back to login form" button (`core/src/components/login/PasswordLessLoginForm.vue:88-113`; `Login.vue:106-121`). The name comes first: `startAuthentication(loginName)` returns that account's credentials as `allowCredentials`, and an account with none gets "Your account is not setup for passwordless login." (`core/src/services/WebAuthnAuthenticationService.ts:21-30`; `lib/private/Authentication/WebAuthn/Manager.php:147-171`). No conditional mediation (High).
2. **Enrolment.** Personal settings → Security, a section "Passwordless Authentication": "Set up your account for passwordless authentication following the FIDO2 standard." It lists "The following devices are configured for your account:", or "No devices configured." (`apps/settings/src/components/WebAuthn/WebAuthnSection.vue:8-30`). Each row is an icon, the name ("Unnamed device" if blank) and a menu with Delete. There are no dates, and the list is sorted by name (`WebAuthnDevice.vue:7-15`; `WebAuthnSection.vue:95-97`). "Add WebAuthn device" asks the browser first ("Please authorize your WebAuthn device."), then for a "Device name" (`WebAuthnAddDevice.vue:15-36`). Adding and deleting both require the password again: the three settings endpoints carry `#[PasswordConfirmationRequired]` (`apps/settings/lib/Controller/WebAuthnController.php:44-82`), and the front end calls `confirmPassword()` before registering and before deleting (`WebAuthnAddDevice.vue:140, 155`; `WebAuthnSection.vue:107-116`). Delete has no other confirmation (High).
3. **HTTPS and the relying party.** The RP ID is the request's server host with the port stripped (`Manager.php:50-55, 143-145`; `WebAuthnController.php:51`, `$this->request->getServerHost()`), so it follows whichever trusted domain the person used. On HTTP and not on localhost, the sign-in page shows "Your connection is not secure. Passwordless authentication is only available over a secure connection." (`PasswordLessLoginForm.vue:116-121`), and settings shows "Passwordless authentication requires a secure connection." (`WebAuthnAddDevice.vue:6-9`). An unsupported browser gets "Browser not supported" and "Your browser does not support WebAuthn." An administrator can turn WebAuthn off with `auth.webauthn.enabled` (`Manager.php:234-240`) (High).
4. **Changing the password.** Personal settings → Security → "Password": Current password and New password, with no confirm field, and a "Change password" button (`apps/settings/src/components/PasswordSection.vue:42-73`). The server checks the old password under brute-force protection (`apps/settings/lib/Controller/ChangePasswordController.php:45-82`). Nothing in the form mentions other sessions. Behind it, only the current session's stored password is updated (`lib/private/User/Session.php:1130-1140`). Every other session token is checked again at most every five minutes, and a token whose stored password no longer works is marked invalid and logged out (`Session.php:711-765`). Sessions started by passkey hold no password and are not ended this way (`Session.php:729-740`) (High, read and not run).
5. **Limits and settings.** No limit found. Registration: user verification "preferred", no resident key, attestation "none", ES256 and RS256, 60-second timeout. Already-registered credentials are not excluded (`$excludedPublicKeyDescriptors = []`) (`Manager.php:63-93`). Sign-in asks for user verification "required", unless any of the account's credentials was registered without it, in which case "discouraged" (`Manager.php:150-155`). The challenge is kept in the PHP session (`core/Controller/WebAuthnController.php:56-59`) (High).

## authentik (added, for passkey autofill)

Source: github.com/goauthentik/authentik `main` at `f24849562f3728f6a4e63859c1566e54be165b89` (2026-10-19). It is the only app read that uses conditional mediation.

## The specification on addresses (High)

From [Web Authentication Level 3](https://www.w3.org/TR/webauthn-3/), W3C, dated 2026-08-25:

- "The RP ID must be equal to the origin's effective domain, or a registrable domain suffix of the origin's effective domain." The origin's scheme must be `https`, or its host must be `localhost` over `http`. "The origin's port is unrestricted." (§ 4, *RP ID*).
- An IP address cannot be a relying party: "If effective domain is not a valid domain, then throw a "SecurityError" DOMException. Note: An effective domain may resolve to a host, which can be represented in various manners, such as domain, ipv4 address, ipv6 address … Only the domain format of host is allowed here." (§ 5.1.3 and § 5.1.4, the `effectiveDomain` step). **An instance reached at a LAN IP address cannot offer passkeys over any scheme.**
- Related origins (§ 5.11) let one RP ID be used from up to a handful of other origins listed at `/.well-known/webauthn`. That is what Immich's "Additional domains" publishes.
- Conditional mediation needs a form field whose `autocomplete` ends in the `webauthn` token, "username webauthn" or "current-password webauthn" (§ 5.1.4, the conditional mediation steps).
- The spec's own registration example has the server "also storing a friendly name for later use" (§ 1.3.1).

### webauthn-rs (kanidm)

- **Releases.** Stable `0.5.5` (2026-04-30). Before it: 0.5.4 (2025-12-10), 0.5.3 (2025-10-23), 0.5.2 (2025-07-04), 0.5.1 (2024-12-20), 0.5.0 (2024-04-28). Prereleases `0.6.0-dev` (2026-03-20) and `0.6.1-dev` (2026-04-30). The repository was last pushed 2026-10-12. Three crates move together: `webauthn-rs` is the safe API, `webauthn-rs-core` is the ceremony and cryptography underneath, and `webauthn-rs-proto` holds the JSON types the browser sees. The crate's own documentation directs applications to the safe API. `-core` exists for people who need what the safe API refuses (custom policy, attestation details), as Vaultwarden's JSON edits show.
- **OpenSSL.** In 0.5.5, `webauthn-rs-core` depends on `openssl ^0.10.75` and `openssl-sys ^0.9.111` with no feature to turn them off (`webauthn-rs-core-0.5.5/Cargo.toml:70-74`; its `[features]` has only `default = []`). In 0.6.1-dev, `webauthn-rs-core` depends on `crypto-glue` (RustCrypto: `p256`, `p384`, `rsa`, `x509-cert`), and the lock file names no `openssl` crate (`webauthn-rs-0.6.1-dev/Cargo.lock`). The tracking issue is [#499 "Drop openssl"](https://github.com/kanidm/webauthn-rs/issues/499). On [#587](https://github.com/kanidm/webauthn-rs/issues/587) "Any chance of a stable 0.6.1 release (not -dev)?", maintainers wrote "openssl is dropped" (2026-09-22) and "it is close", with a working v0.6 demo site still to finish (2026-09-24). For comparison, Kamosu's `Cargo.lock` today holds `openssl-probe` (through `rustls-native-certs`) and no `openssl` crate: its TLS is rustls.
- **Features** (identical in 0.5.5 and 0.6.1-dev): `default = ["attestation"]`, plus `conditional-ui`, `danger-allow-state-serialisation`, `danger-credential-internals`, `resident-key-support`, `danger-user-presence-only-security-keys`, `workaround-google-passkey-specific-issues`.
- **Passkey API, by button.** `start_passkey_registration(user_unique_id: Uuid, user_name, user_display_name, exclude_credentials) -> (CreationChallengeResponse, PasskeyRegistration)`, then `finish_passkey_registration(&RegisterPublicKeyCredential, &PasskeyRegistration) -> Passkey`. Then `start_passkey_authentication(&[Passkey]) -> (RequestChallengeResponse, PasskeyAuthentication)` and `finish_passkey_authentication(…) -> AuthenticationResult`, whose counter and backup state the caller writes back to the stored `Passkey` (`src/lib.rs:534-730`). Registration always asks for user verification "required", attestation "none", `credProtect` and `credProps` (`:538-575`).
- **Username-less and autofill** are behind `conditional-ui`. `start_discoverable_authentication() -> (RequestChallengeResponse, DiscoverableAuthentication)` sends no allowed credentials and sets `mediation = Conditional`, with the comment "Force conditional ui - this is not a generic discoverable credential workflow!". `identify_discoverable_authentication(&PublicKeyCredential) -> (Uuid, &[u8])` returns the user's UUID and credential ID so the caller can load that user's keys, and `finish_discoverable_authentication(…, &[DiscoverableKey])` finishes; a `DiscoverableKey` is made `From<&Passkey>` (`src/lib.rs:1310-1394`; `src/interface.rs:615-690`). The `mediation` field is only part of the JSON sent to the browser, so a page can still make a plain button call with the same options (`webauthn-rs-proto-0.5.5/src/auth.rs:38-69`).
- **A trap for a username-less button.** `start_passkey_registration` calls `.require_resident_key(false)`, which the core turns into `residentKey: "discouraged"` (`webauthn-rs-0.5.5/src/lib.rs:565`; `webauthn-rs-core-0.5.5/src/core.rs:298-302`; unchanged in 0.6.1-dev). Phone and password-manager passkeys are usually discoverable anyway, but a security key may not be, and then it cannot answer a username-less request. Every app above that signs in without a name asks for `residentKey: required` instead. In webauthn-rs, the caller can set `authenticator_selection.resident_key` on the returned `CreationChallengeResponse` before sending it; the field is public (`webauthn-rs-proto-0.5.5/src/options.rs:302-324`) and the finish step ignores it (`core.rs:393`). That is an inference from the source, not something the crate documents.
- **State between start and finish.** `PasskeyRegistration`, `PasskeyAuthentication` and `DiscoverableAuthentication` derive `Serialize` and `Deserialize` only with `danger-allow-state-serialisation`. The crate explains: this value "*MUST* be persisted on the server. If you store this in a cookie or some other form of client side stored value, the client can replay a previous authentication state", and serialising to a database, or a cookie that is only a key into a server-side map, is safe (`src/lib.rs:83-103`). `Passkey` itself always serialises, and "can be safely serialised and deserialised from a database" (`src/interface.rs:53-57`). Vaultwarden turns the feature on and writes state as JSON into a database row.

### passkey-rs (1Password)

`passkey`, `passkey-client` and `passkey-authenticator` `0.6.0` (2026-10-01). It is "a collection of Rust libraries to enable developers to use Passkeys in Rust code" through a WebAuthn client and a CTAP2 authenticator, and "It is not within the scope of these libraries to manage the details of the interaction with the Relying Party" (`passkey-0.6.0/README.md`). It is the other side of the exchange: a software authenticator, not a server. Its cryptography offers an `aws-lc-rs` feature (`Cargo.toml:47`). Where it could help Kamosu is as a stand-in authenticator in Rust tests of the server ceremony. That is an inference; no app read uses it that way.

### webauthn_rp

`webauthn_rp 0.3.0` (2025-04-03; 0.2.5 to 0.2.7 in March 2025), hosted at git.philomathiclife.com rather than GitHub. A server-side relying-party crate on pure RustCrypto (`ed25519-dalek`, `p256`, `p384`, `rsa`), with no OpenSSL. Its README example keeps ceremony state in an in-memory `FixedCapHashSet`, and a `serializable_server_state` feature lets state be stored elsewhere (`webauthn_rp-0.3.0/Cargo.toml`, `README.md`). It has had no release in 18 months. I did not read its API further.

## Browser side

- **Native JSON helpers.** `PublicKeyCredential.parseCreationOptionsFromJSON()`, `parseRequestOptionsFromJSON()` and `PublicKeyCredential.toJSON()` shipped in Chrome 129, Firefox 119 and Safari 18.4, with Edge, Chrome for Android, Firefox for Android and Safari on iOS following their engines (MDN browser-compat-data, `api/PublicKeyCredential.json` at `6aa0e14f08`, 2026-08-18). MDN marks them "Baseline 2025 Newly available. Since March 2025, this feature works across the latest devices and browser versions." and "available only in secure contexts" ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/PublicKeyCredential/parseCreationOptionsFromJSON_static)). `isConditionalMediationAvailable()` dates from Chrome 108, Firefox 119 and Safari 16. `getClientCapabilities()` from Chrome 133, Firefox 135 and Safari 17.4 (same file). A phone on iOS older than 18.4 would lack the parse helpers (High).
- **`@simplewebauthn/browser`** `14.0.0` (npm, 2026-09-02, MIT, no dependencies, 295 kB unpacked). `startRegistration({ optionsJSON, useAutoRegister })` and `startAuthentication({ optionsJSON, useBrowserAutofill })` convert base64url to buffers by hand rather than through the native helpers (`packages/browser/src/methods/startRegistration.ts:40-52`). `useBrowserAutofill` runs conditional mediation and checks that an input with the `webauthn` token is present. `browserSupportsWebAuthn()` is simply `typeof PublicKeyCredential === 'function'` (`helpers/browserSupportsWebAuthn.ts`), and a `SecurityError` is turned into "… is an invalid domain" or "The RP ID … is invalid for this domain" (`helpers/identifyRegistrationError.ts:100-112`). Immich and Nextcloud use it. Gitea and Bitwarden call `navigator.credentials` themselves (High).

## What this means for Kamosu

**Consensus** marks a pattern every app read agrees on. **Differs** marks a point where they part, which becomes a design question for #370.

1. **Consensus: passkeys sit beside the password, never in place of it.** A secondary button or link under the name and password form, with an "or" between them where there is one. Nobody hides the password form when passkeys exist.
2. **Consensus: sign in without asking for a name first.** Immich, Bitwarden and Gitea send no `allowCredentials`, and each registers with `residentKey: required` and `userVerification: required`. With webauthn-rs that means the `conditional-ui` feature for the discoverable calls, and setting `resident_key` on the registration challenge, since `start_passkey_registration` asks for "discouraged". Nextcloud's name-first form is the outlier.
3. **Differs: passkey autofill in the name field.** Only authentik does it (`autocomplete="username webauthn"` plus conditional mediation). webauthn-rs's discoverable start is built for it. It is a choice between a button alone and a button plus autofill.
4. **Consensus: attestation "none", one row per passkey with a name, a delete that asks first, and existing credentials excluded at registration.** Nextcloud's missing exclusion is the exception.
5. **Differs: where the name comes from.** Typed before (Gitea), typed after (Bitwarden, Nextcloud), or filled from the AAGUID and renamable (Immich, authentik). Immich's fallback order is AAGUID, then device and system, then "Passkey".
6. **Differs: what the list shows, and whether adding asks for the password.** Dates range from none (Bitwarden, Nextcloud) to created and last used (Immich). Re-entering the password is asked by Bitwarden and Nextcloud, not by Immich or Gitea. Bitwarden alone caps the count, at five.
7. **Consensus: one fixed relying party when the app has a public URL setting.** Vaultwarden, Bitwarden and Gitea all take the configured URL's host, which matches the issue's "the public address's host". Only Immich tells the person that changing the domain ends existing passkeys, and only Immich publishes related origins. What Kamosu says when the public address changes is open.
8. **Differs: what a person sees when passkeys cannot work.** Nextcloud and Gitea say why in a sentence. Immich and Bitwarden hide the button. Per the spec, an instance reached at an IP address can never offer passkeys, so a LAN-only instance falls in this case, and so does a development instance on an IP.
9. **Differs: changing a password and other sessions.** Every app asks for the current password. Three of four have a confirm field. On other sessions the four disagree: an option off by default (Immich), always ended with a warning (Bitwarden and Vaultwarden), or ended without a word (Nextcloud, Gitea). No app offers to end API keys or access keys with it. The issue's "offered to be ended" matches Immich's switch, and its default is the open question.
10. **Differs: which webauthn-rs.** Stable 0.5.5 links OpenSSL, which Kamosu's tree does not have today. 0.6.1-dev drops it but is a prerelease that `cargo add` will not pick by default. Whether to take 0.5.5 with OpenSSL now or wait for 0.6 is a decision for the ticket. On the browser side, the native JSON helpers are Baseline 2025 and need no library. They exclude iOS before 18.4, which `@simplewebauthn/browser` would still cover.
